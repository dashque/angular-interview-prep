Карта тем

На собеседовании редко спрашивают определение ради определения. Обычно хотят понять, умеете ли вы проводить границы: где заканчивается UI, где начинается сценарий экрана, где живёт контракт API и как не сломать всё приложение обновлением одного сервиса. В каждом большом разделе ниже есть блок «зачем придумали / какие проблемы закрыли / как сделать своё».

SOLID

Пять принципов Роберта Мартина о том, как проектировать классы и модули так, чтобы изменения не расползались по всей системе.

GRASP

Девять принципов Крэга Лармана о том, какому объекту какую ответственность отдать, ещё до выбора конкретного паттерна GoF.

DDD Strategic

Стратегическая часть предметно-ориентированного проектирования: где проходит граница модели, какой язык у команды и как несколько моделей стыкуются друг с другом.

BFF

Отдельный backend под конкретный frontend, чтобы не заставлять один общий API обслуживать сразу все клиенты одинаково плохо.

SemVer и теги

Правила версионирования публичного контракта зависимости, когда бэкенд-клиент лежит в package.json и обновляется по тегу.

SOLID

SOLID — это пять принципов объектно-ориентированного проектирования, которые систематизировал Роберт Мартин (Uncle Bob). Их общая идея: код должен оставаться удобным для изменений. Если зависимости между модулями спроектированы плохо, любое небольшое требование тянет за собой правки в десятках файлов. Если хорошо — меняется узкий слой, а остальная система продолжает работать.

Solid Relevance (Martin) Статья про SRP Статья про OCP Wikipedia: SOLID Angular: Dependency injection

Зачем придумали

К 1990–2000-м объектно-ориентированный код уже писали массово, но «классы и наследование» сами по себе не спасали от хрупкости. Роберт Мартин собирал принципы, которые помогают управлять зависимостями: чтобы система старела медленнее и изменения оставались локальными. SOLID — это не ритуал и не чеклист ради галочки, а ответ на боль сопровождения.

Какие проблемы закрыли

Жёстко сцепленные модули, где правка в одном месте ломает другое. «Бог-классы», в которых смешаны UI, сеть, правила и хранение. Невозможность подменить деталь без переписывания сценария. Интерфейсы, которые тащат за собой лишние методы. Невозможность добавить поведение без правки уже работающего кода.

Как сделать своё в Angular

Возьмите один экран и выпишите причины, по которым он менялся за последний месяц. Каждую причину поселите в отдельный модуль: шаблон, facade, api, mapper, storage. Различия стендов и внешних систем вынесите в InjectionToken и providers. Новое поведение добавляйте новой реализацией рядом, а не новой веткой if в старом сервисе.

S — Single Responsibility Principle (принцип единственной ответственности)

«Gather together the things that change for the same reasons. Separate things that change for different reasons.» — Роберт Мартин, Solid Relevance

По-русски это звучит так: собирайте вместе то, что меняется по одной причине, и разделяйте то, что меняется по разным причинам. Часто принцип упрощают до фразы «у класса должна быть одна ответственность», но важнее смотреть именно на причину изменения. Один файл может содержать несколько методов — это нормально, если все они относятся к одной оси изменений.

Как это выглядит в Angular

Представьте экран списка заказов. У него есть как минимум четыре разные причины меняться: внешний вид таблицы, HTTP-контракт сервиса заказов, правила «можно ли отменить заказ» и способ сохранения черновика фильтра в браузере. Если всё это лежит в одном компоненте, любое из этих изменений заставляет править один и тот же большой файл.

  • OrderListComponent отвечает только за отображение и за пользовательские события: клик, выбор строки, открытие модалки.
  • OrdersApi знает только про HTTP: какой URL вызвать, какой тип ответа ожидать, как передать параметры запроса.
  • Facade или SignalStore координирует сценарий экрана: загрузил данные, обработал ошибку, обновил состояние, при необходимости перешёл на другой route.
  • Функция или модуль toOrder(dto) отвечает за перевод сырого ответа API в удобную для экрана модель. Этот код меняется, когда меняется контракт API, а не когда дизайнер просит другой цвет кнопки.

Типичное нарушение: компонент сам вызывает HttpClient, сам превращает ответ в строки таблицы, сам считает, можно ли отменить заказ, и сам пишет что-то в localStorage. Такой компонент трудно тестировать и ещё труднее объяснять на интервью как «чистую архитектуру».

O — Open/Closed Principle (принцип открытости/закрытости)

«A Module should be open for extension but closed for modification.» — Роберт Мартин, Solid Relevance

Модуль должен быть открыт для расширения и закрыт для изменения. Идея в том, чтобы новое поведение можно было добавить, не переписывая уже проверенный код, который этим поведением пользуются другие части системы. На практике это почти всегда означает: выделить абстракцию и подключать новые реализации рядом со старыми.

Как это выглядит в Angular

Допустим, сегодня оплата идёт только картой, а завтра добавляют СБП. Плохой путь — открыть старый PaymentService и вписать ещё одну ветку if (type === 'sbp'). Хороший путь — завести абстракцию стратегии оплаты и зарегистрировать новую реализацию через DI.

  • Новая стратегия оплаты подключается через provide / InjectionToken, а код checkout-сценария продолжает зависеть от абстракции, а не от конкретного класса.
  • Цепочку HTTP можно расширять без правки HttpClient: в документации Angular это делается через provideHttpClient(withInterceptors([...])). Новый interceptor — это расширение пайплайна, а не модификация ядра.
  • Новый стенд тоже лучше подключать конфигурацией providers, а не новыми условиями внутри уже существующих feature-сервисов.

L — Liskov Substitution Principle (принцип подстановки Лисков)

«A program that uses an interface must not be confused by an implementation of that interface.» — Роберт Мартин, Solid Relevance

Программа, которая работает через интерфейс, не должна «удивляться» конкретной реализации этого интерфейса. Исторически принцип связан с работой Барбары Лисков: объект подтипа можно подставить вместо объекта супертипа, и программа по-прежнему останется корректной. Для фронтенда удобнее формулировка через контракт: любая реализация токена или интерфейса должна соблюдать обещания, на которые рассчитывает вызывающий код.

Как это выглядит в Angular

  • Functional interceptor обязан принять запрос и вернуть поток Observable<HttpEvent> через вызов next. Если один interceptor молча глотает ошибки или меняет смысл ответа без явного контракта, он нарушает ожидания всей цепочки. См. HTTP interceptors.
  • Представьте токен AuthTokenProvider с реализациями для локальной разработки и для production. Обе реализации должны отдавать токен в одном и том же смысле: либо строку access token, либо явно задокументированное отсутствие токена. Если «dev-реализация» иногда возвращает случайный мусор, facade будет вести себя по-разному только на одном стенде — это и есть нарушение подстановки.

I — Interface Segregation Principle (принцип разделения интерфейса)

«Keep interfaces small so that users don’t end up depending on things they don’t need.» — Роберт Мартин, Solid Relevance

Держите интерфейсы маленькими, чтобы клиент не зависел от методов, которые ему не нужны. Иначе изменение «чужого» метода в огромном интерфейсе заставляет пересобирать и пересматривать код, которому этот метод никогда не был нужен.

Как это выглядит в Angular

Вместо одного гигантского сервиса BackendApi с десятками методов лучше завести отдельные клиенты: OrdersApi, CatalogApi, UsersApi. Экран каталога тогда зависит только от каталога. Когда команда заказов выпускает MAJOR-версию своего пакета, приложение каталога не обязано срочно обновляться только потому, что когда-то всё было свалено в один интерфейс.

В monorepo тот же принцип проявляется на уровне библиотек: наружу через index.ts экспортируйте только публичный API. Внутренние mapper’ы и helper’ы оставляйте приватными для библиотеки, чтобы соседние features не цеплялись к деталям реализации.

D — Dependency Inversion Principle (принцип инверсии зависимостей)

«Depend in the direction of abstraction. High level modules should not depend upon low level details.» — Роберт Мартин, Solid Relevance

Зависимости должны быть направлены в сторону абстракций. Высокоуровневый модуль не должен знать низкоуровневые детали. Проще: сценарий «оформить заказ» не должен импортировать конкретный класс, который ходит в Stripe. И сценарий, и адаптер Stripe зависят от общего порта — интерфейса или InjectionToken.

Как это выглядит в Angular

Angular изначально построен вокруг dependency injection, поэтому DIP здесь не теория «на вырост», а повседневный механизм фреймворка. Официальные гайды: Dependency injection in Angular, Defining dependency providers.

  • Высокоуровневый код: CheckoutFacade получает зависимость через inject(PAYMENT_PORT) и не знает, какая именно реализация подставлена.
  • Низкоуровневый код подключается снаружи: в app.config.ts или в providers конкретного стенда вы пишете { provide: PAYMENT_PORT, useClass: StripeAdapter }.
  • Разные стенды отличаются набором providers и значениями вроде API_BASE_URL. Компоненты при этом не читают environment.name и не ветвятся по строке 'stage2' — они всегда работают с абстракцией. 
export const API_BASE_URL = new InjectionToken<string>('API_BASE_URL');

export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(withInterceptors([authInterceptor])),
    { provide: API_BASE_URL, useValue: environment.apiBaseUrl },
  ],
};

GRASP

GRASP расшифровывается как General Responsibility Assignment Software Patterns (или Principles). Это набор из девяти фундаментальных принципов о том, как назначать ответственность объектам. Их описал Крэг Ларман в книге Applying UML and Patterns. Если SOLID больше про устойчивость структуры и направление зависимостей, то GRASP отвечает на более ранний вопрос: кому именно поручить работу, когда вы только проектируете взаимодействие объектов.

Wikipedia: GRASP Larman, глава 16 (O’Reilly)

Зачем придумали

Ларман заметил, что люди часто знают паттерны GoF и умеют рисовать UML, но спотыкаются на более базовом шаге: кому отдать ответственность. GRASP появился как учебный набор именованных принципов, чтобы это решение можно было обсуждать вслух, а не делать «на ощупь».

Какие проблемы закрыли

Анемичные модели, где объекты только хранят поля, а один сервис командует всеми. Случайное создание объектов «кто попало». Смешение входа из UI с бизнес-сценарием. Жёсткие связи с инфраструктурой внутри доменных понятий. Системы, которые невозможно безопасно менять, потому что вариации не изолированы.

Как сделать своё в Angular

Для нового сценария сначала сформулируйте ответственность одним предложением: «кто принимает клик», «кто решает canCancel», «кто ходит в HTTP». Потом назначьте её по GRASP: Expert для правил рядом с данными, Controller для facade, Pure Fabrication для api/interceptor, Indirection и Protected Variations для границы с API. Если назначение спорное — проверьте cohesion/coupling: не стало ли хуже.

High Cohesion и Low Coupling

High Cohesion означает, что обязанности внутри элемента логически связаны и сфокусированы на одной теме. Low Coupling означает, что элемент мало знает о других элементах и слабо от них зависит. Вместе эти два принципа задают «здравый смысл» модульности: внутри — плотность смысла, снаружи — немного связей. — GRASP / Larman; обзор: Wikipedia

Как это выглядит в Angular

Feature-библиотека или папка orders должна содержать то, что относится к заказам: маршруты, компоненты, facade, API-клиент, мапперы. Если эта же библиотека напрямую лезет во внутренние файлы billing, связанность между модулями растёт, и любое изменение биллинга начинает ломать заказы.

В workspace с несколькими приложениями общая UI-kit библиотека — нормальная низкосвязанная зависимость: кнопки и формы редко несут смысл предметной области. А вот одна общая «модель всего бизнеса» на все apps обычно повышает coupling и в итоге мешает командам развивать продукты независимо.

Information Expert

«Assign a responsibility to the information expert — the class that has the information necessary to fulfill the responsibility.» — Крэг Ларман, Information Expert; Applying UML and Patterns

По-русски: поручайте задачу тому классу, у которого уже есть информация, необходимая для её выполнения. Это помогает не плодить «анемичные» объекты, у которых есть только поля, а вся логика живёт в одном огромном сервисе-командире.

Как это выглядит в Angular

Правило «можно ли отменить заказ» почти наверняка зависит от статуса заказа, времени создания и, возможно, от роли пользователя. Если все нужные данные уже собраны в модели заказа или во view-model, именно там и стоит жить проверке canCancel — как методу или как чистой функции рядом с типом. Копировать одно и то же условие в три компонента — значит нарушать Expert и одновременно плодить баги рассинхрона.

Важная оговорка Лармана: если следование Expert затаскивает в доменный объект инфраструктуру (например, заказ сам умеет ходить в HTTP), выигрыш в «экспертности» быстро превращается в проигрыш по связности. Тогда ответственность выносят в искусственный объект — см. Pure Fabrication ниже.

Creator

Ответственность за создание объекта B стоит отдать объекту A, если A содержит B, агрегирует B, активно использует B или уже обладает данными, нужными для инициализации B. Упрощённо Creator — это Information Expert, применённый именно к моменту создания. — GRASP Creator (Larman)

Как это выглядит в Angular

Когда с сервера приходит DTO, создавать удобную для экрана модель должен тот слой, который владеет этими данными и дальше с ними работает: mapper, store или facade. Компоненту незачем знать, какие поля обязательны для конструктора доменного объекта, и незачем размазывать new Order(...) по шаблонной логике.

Не путайте Creator с Angular DI. DI решает, кто создаст сервис и как долго он будет жить в injector’е. Creator из GRASP — про ответственность за рождение доменных или view-model объектов внутри сценария.

Controller

Назначьте ответственность за обработку системного события объекту, который представляет систему в целом или один use-case. Этот объект стоит первым после входа извне и координирует дальнейшую работу, но не обязан сам содержать всю бизнес-логику. — GRASP Controller (Larman)

Как это выглядит в Angular

На UI-уровне контроллером часто выступает компонент: он получает клик или submit и должен быстро делегировать сценарий дальше. На уровне приложения контроллером становится facade, effect или use-case service: именно он знает порядок шагов «проверить корзину → вызвать API → обновить состояние → перейти на страницу успеха».

Плохой Controller — это компонент на несколько сотен строк, в котором одновременно разбирается форма, валидируются бизнес-правила, сериализуется запрос, обрабатываются три HTTP-ответа и вручную клеится навигация. Такой код трудно читать именно потому, что роль «координатора входа» смешалась с ролью «эксперта предметной области» и с ролью «транспортного адаптера».

Pure Fabrication

Создайте искусственный класс, которого нет в словаре предметной области, если это помогает сохранить высокую связность и низкую связанность и не загрязняет бизнес-объекты инфраструктурой. — GRASP Pure Fabrication (Larman)

Как это выглядит в Angular

В языке бизнеса нет сущности «HttpInterceptor» или «SignalStore». Тем не менее эти объекты нужны архитектуре: они держат технические обязанности отдельно от экрана и от правил заказа. То же самое относится к OrdersApi, к ErrorMapper и к тонкому storage-адаптеру для localStorage.

Pure Fabrication — это разрешение инженеру ввести конструкцию «ради кода», когда буквальный перенос всех обязанностей в бизнес-объект сделал бы систему хуже.

Indirection

Назначьте ответственность промежуточному объекту, чтобы развязать другие компоненты и уменьшить жёсткую связанность между ними. — GRASP Indirection (Larman)

Многие знакомые паттерны — Adapter, Facade, Proxy, Repository — по сути являются разными формами одной и той же идеи: между двумя сторонами появляется управляемая прослойка.

Как это выглядит в Angular

  • Facade стоит между компонентом и несколькими API-сервисами, чтобы шаблон не знал про зоопарк клиентов.
  • Mapper DTO → view-model стоит между сырым контрактом пакета API и тем, что удобно показывать в шаблоне.
  • Interceptor стоит между feature-кодом и транспортом HTTP: добавляет токен, логирует, нормализует ошибки.
  • BFF стоит между Angular-приложением и набором микросервисов, если собирать ответ на клиенте слишком дорого или хрупко.

Polymorphism

Когда поведение меняется в зависимости от типа, назначайте ответственность полиморфным операциям. Вместо длинных условных конструкций по типу объекта используйте общую абстракцию и набор реализаций. — GRASP Polymorphism (Larman)

Как это выглядит в Angular

Если retail-приложение и partner-приложение считают цену по-разному, не обязательно размазывать if (appType === 'partner') по сервисам. Можно описать общий контракт стратегии цены и подставить нужную реализацию через providers конкретного app в monorepo. То же самое работает для auth-адаптеров разных стендов: контракт один, реализации разные.

Protected Variations

Найдите места, где изменения наиболее вероятны, и оберните их стабильной точкой вариации — интерфейсом, адаптером, отдельным сервисом, — чтобы эти изменения не пробивали клиентов навылет. — GRASP Protected Variations (Larman); тесно связан с OCP и DIP

Как это выглядит в Angular при многих API и стендах

В вашей вакансии нестабильны как раз внешние границы: контракты десятка сервисов, адреса стендов, форматы ошибок, теги пакетов бэкенда. А для пользователя и для UI-сценария желательно, чтобы экран заказа оставался узнаваемым и относительно стабильным.

Поэтому между шаблоном и внешним миром ставят защиту: слой data-access, маппер в локальную модель, InjectionToken для base URL, зафиксированная версия API-клиента, а при необходимости — BFF с контрактом, специально заточенным под Angular-приложение. Тогда MAJOR у одного микросервиса бьёт по границе, а не по всем компонентам сразу.

Как GRASP стыкуется с SOLID: Open/Closed часто достигается через Polymorphism и Protected Variations; Dependency Inversion — через Indirection и те же точки защиты; Single Responsibility хорошо сочетается с High Cohesion и Information Expert.

DDD и Strategic Design

Domain-Driven Design (предметно-ориентированное проектирование) — подход Эрика Эванса. Его главная мысль: в сложных системах нужно явно работать с предметной областью, говорить с бизнесом на одном языке и отражать этот язык в коде. Strategic Design — это «крупномасштабная» часть DDD: она помогает понять, где модель должна быть единой, а где лучше завести отдельные модели и аккуратно описать связи между ними.

domainlanguage.com (Evans) Fowler: Bounded Context DDD Community

Зачем придумали

Крупные системы пытались описывать одной «правильной» моделью всего бизнеса — и это регулярно заканчивалось противоречиями. Эванс предложил другой ход: признать, что у разных частей продукта разные смыслы одних и тех же слов, и сделать границы модели явными. Strategic Design как раз про это.

Какие проблемы закрыли

Размытый язык между бизнесом и разработкой. Одна сущность Customer, которая одновременно означает всё и ничего. Невозможность менять часть системы, не задевая остальное. Интеграции, где чужая модель протекает внутрь и постепенно разрушает вашу.

Как сделать своё в Angular

Нарисуйте applications и команды рядом с ними. Для каждого app выпишите 10 главных терминов продукта. Если термины расходятся — это разные Bounded Contexts: отдельные модели и отдельные libs. На стыке с API сделайте ACL-маппер. Общим оставляйте только то, что правда общее: ui-kit, логирование, иногда auth-инфраструктуру — но не «всю доменную модель».

Ubiquitous Language (единый язык)

Единый язык модели, на котором говорят и разработчики, и эксперты предметной области. Термины этого языка напрямую отражаются в коде, в тестах и в разговорах команды. — Eric Evans, Domain-Driven Design

Как это выглядит в Angular

Если продукт говорит «черновик заявки», не называйте сущность в коде TempOrderDraftEntity без необходимости. Имена типов, signals, route’ов и текстов ошибок должны совпадать с языком команды. Когда в клиентском портале говорят «заказ», а в админке — «заявка», это уже сигнал, что перед вами могут быть разные модели, даже если JSON с бэкенда выглядит похоже.

Bounded Context (ограниченный контекст)

«A description of a boundary (typically a subsystem, or the work of a particular team) within which a particular model is defined and applicable.» — Eric Evans

Vaughn Vernon уточняет practically ту же мысль: Bounded Context — это явная граница, внутри которой существует конкретная модель, а все термины Ubiquitous Language имеют точный смысл. Martin Fowler подчёркивает, что именно Bounded Context стоит в центре strategic design: большую систему делят на контексты и явно описывают их взаимосвязи, потому что полная унификация одной гигантской модели обычно нереалистична. Источник: martinfowler.com/bliki/BoundedContext.

Как это выглядит в Angular workspace

Несколько приложений в одном репозитории — хороший кандидат на несколько Bounded Contexts. Например, client-portal, partner-cabinet и ops-admin могут по-разному понимать, кто такой «клиент» и что такое «заказ». Общий JSON с бэкенда сам по себе ещё не повод завести один TypeScript-тип на все приложения.

Практичная раскладка: доменные модели живут рядом со своим приложением или feature-библиотекой, а в shared остаются вещи вроде ui-kit, логирования и, осторожно, инфраструктуры аутентификации. Папка называется shared — это ещё не значит, что туда можно свалить всю предметную область.

Context Map и отношения между контекстами

Context Map — это карта Bounded Contexts и отношений между ними: кто является источником контракта, кто потребителем, и каким способом модели переводятся друг в друга. — Evans, Part IV Strategic Design; Vernon, Implementing Domain-Driven Design, глава про context mapping

На интервью достаточно уверенно объяснить несколько базовых отношений:

  • Customer/Supplier — upstream-команда задаёт контракт, downstream-команда его потребляет. Часто это выглядит как «команда API определила OpenAPI, Angular-команда подстроилась».
  • Conformist — потребитель принимает модель поставщика почти без сопротивления. Так бывает, когда фронт не может влиять на форму DTO и вынужден жить «как прислали».
  • Anti-Corruption Layer (ACL) — слой перевода, который не даёт чужой модели протечь внутрь вашего контекста.
  • Shared Kernel — небольшое действительно общее ядро. Это редкий и дорогой инструмент, а не оправдание для свалки всего кода в libs/shared/domain.

Anti-Corruption Layer на фронтенде

Самый частый ACL в Angular — это маппер из DTO пакета API в локальную модель экрана или домена приложения. Шаблон и facade работают уже с понятными полями вроде status: 'paid', а не с сырым status_code: 2 из чужого контракта. Когда вы обновляете тег зависимости, правите в первую очередь границу ACL, а не половину компонентов. 

// контракт зависимости / OpenAPI
type OrderDto = { order_id: string; status_code: number };

// модель контекста Angular-приложения
type Order = { id: string; status: 'new' | 'paid' | 'cancelled' | 'unknown' };

export function toOrder(dto: OrderDto): Order {
  // перевод чужого контракта в язык вашего приложения
}

BFF — Backend for Frontend

BFF — архитектурный паттерн: для конкретного frontend-интерфейса делают отдельный backend-слой, вместо того чтобы заставлять один общий API одинаково хорошо служить всем клиентам сразу. Идею популяризировал Sam Newman; Microsoft включила её в Azure Architecture Center как отдельный pattern.

Microsoft Learn: Backends for Frontends Sam Newman: BFF Habr: обзор BFF

Зачем придумали

Когда у продукта появилось несколько клиентов — web, mobile, встраиваемые виджеты — один general-purpose API перестал быть удобным для всех. Sam Newman описал BFF как способ дать каждому frontend свой backend-слой и не заставлять общий сервис вечно разрываться между чужими требованиями. Microsoft позже закрепила это в Architecture Center.

Какие проблемы закрыли

Конфликт релизов между командами разных клиентов. Лишние поля и неудобная пагинация «для всех сразу». Хрупкие waterfall-запросы из браузера к десятку микросервисов. Необходимость светить внутренние API клиенту. Сложность подогнать payload под ограничения конкретного канала.

Как сделать своё рядом с Angular

Выберите один экран или одно приложение с самой болезненной склейкой данных. Опишите контракт ответа «как удобно UI», а не «как удобно микросервисам». Поднимите тонкий BFF, который ходит в нужные сервисы, собирает ответ и отдаёт OpenAPI клиенту. В Angular оставьте один сгенерированный клиент и facade. Не тащите в BFF ядро домена — только client-specific сборку и адаптацию.

Официальная формулировка Microsoft

«Create a separate backend service for each frontend interface, instead of using a single general-purpose backend for all of them. This approach lets you tailor each backend to the needs of its frontend…» — Backends for Frontends pattern; в основе лежит паттерн Sam Newman

Перевод смысла: создайте отдельный backend-сервис для каждого frontend-интерфейса, вместо одного универсального backend на всех. Так каждый backend можно подогнать под нужды своего клиента и не превратить общий сервис в место вечного конфликта требований.

Типичная проблема выглядит так. Сначала есть web-клиент и один backend. Потом появляется mobile. У мобильного клиента другие ограничения по сети, другой экран, другая пагинация, другой набор полей. Если продолжать гнуть один API под всех, этот API начинает обрастать специальными флагами, а команды фронтенда ждут друг друга на каждом релизе.

Microsoft отдельно подчёркивает несколько важных ограничений паттерна:

  • В BFF должна жить логика, специфичная для пользовательского опыта конкретного клиента. Сквозные вещи вроде периметра авторизации, rate limiting и маршрутизации лучше оставлять gateway-слою.
  • Некоторое дублирование кода между разными BFF — ожидаемая цена за независимость клиентов.
  • Появляется дополнительный сетевой hop, а значит может вырасти latency. Не нужно плодить BFF «на всякий случай».
  • Если все клиенты ходят почти одинаково, отдельный BFF может быть лишним: хватит общего backend или API gateway.

Как это стыкуется с Angular-проектом

Для Angular-приложения BFF — это стабильный контракт «под наш UI». В идеальном случае экран зависит от одного клиента вроде OrdersBffClient, сгенерированного из OpenAPI, а не от десяти разных микросервисных клиентов, которые компонент или даже facade вынужден склеивать самостоятельно.

  • Base URL в environment указывает на BFF конкретного стенда. Подробнее про HTTP-слой Angular: HttpClient guide.
  • Facade остаётся координатором use-case: он вызывает методы BFF, обновляет signals и решает, что показать пользователю. Но тяжёлую агрегацию «профиль + заказ + платежи + доставка» по возможности лучше делать на BFF, а не длинным waterfall’ом из браузера.
  • Если в monorepo несколько приложений, у них вполне могут быть разные BFF. Это прямо следует из определения паттерна: отдельный backend под отдельный frontend interface.

Только Angular data-access

В приложении много мелких API-сервисов. Facade сам собирает экран из нескольких ответов. Это нормально, пока запросов мало и контракты относительно стабильны. Но каждый микросервис может сломать UI своей MAJOR-версией.

Angular плюс BFF

Приложение зависит от контракта, заточенного под канал или экран. Агрегация и подгонка формата происходят на сервере. Для UI это сильный Protected Variations: внутренние сервисы могут меняться, пока BFF сохраняет обещанный контракт.

Версионирование: бэкенд как зависимость по тегам

На многих проектах фронтенд подключает OpenAPI-клиент, npm-пакет или git-dependency бэкенда прямо в репозиторий и обновляет его по тегу. С точки зрения архитектуры вы версионируете не «весь бэкенд мира», а публичный контракт на границе вашего Angular-контекста.

Semantic Versioning 2.0.0 npm: About semantic versioning npm: dependencies в package.json

Зачем придумали

SemVer появился как способ передавать смысл изменения номером версии, а не словами «вроде совместимо». Tom Preston-Werner формализовал правила, чтобы зависимость можно было обновлять предсказуемо: понять по MAJOR/MINOR/PATCH, будет ли поломка. В связке с npm и git-тегами это стало практикой поставки контрактов между командами.

Какие проблемы закрыли

Dependency hell: слишком жёсткие зависимости блокируют обновления, слишком свободные — приносят скрытые поломки. Непонятно, можно ли поднимать пакет без срочного релиза всех потребителей. Фронтенд и бэкенд расходятся по стендам без явного сигнала о совместимости.

Как сделать своё в Angular-репозитории

Зафиксируйте, что именно является публичным API зависимости: OpenAPI, npm-клиент, набор DTO. Договоритесь: ломающее изменение поля = MAJOR. В CI смотрите diff контракта при обновлении тега. В приложении держите ACL-маппер как подушку безопасности. Перед выкладкой сверяйте версию клиента в lockfile с версией сервиса на стенде.

Что говорит спецификация SemVer

Given a version number MAJOR.MINOR.PATCH, increment the:
1. MAJOR version when you make incompatible API changes
2. MINOR version when you add functionality in a backward compatible manner
3. PATCH version when you make backward compatible bug fixes — semver.org, автор Tom Preston-Werner

Если говорить по-русски: номер версии имеет вид MAJOR.MINOR.PATCH. MAJOR поднимают, когда публичный API меняется несовместимо. MINOR поднимают, когда добавляют обратно совместимую функциональность. PATCH поднимают, когда делают обратно совместимые исправления ошибок.

Спецификация требует, чтобы программное обеспечение, заявляющее SemVer, явно определило свой публичный API — в документации, в коде или и там, и там. После того как версия опубликована, её содержимое нельзя молча менять: любое изменение выпускается уже как новая версия. Пока пакет в зоне 0.y.z, API считается нестабильным и может меняться свободно.

Как это выглядит в Angular-репозитории

Зависимость может быть обычным npm-пакетом с точной версией или git-зависимостью с тегом. В обоих случаях идея одна: в lockfile зафиксировано, с каким контрактом собран фронтенд. 

// package.json
{
  "dependencies": {
    "@company/orders-bff-client": "1.8.3",
    "@company/catalog-api": "git+ssh://git@github.com/company/catalog-api.git#v3.2.1"
  }
}

Рабочий процесс обновления обычно такой:

  1. Поднимаете версию или тег в package.json и обновляете lockfile.
  2. Если клиент генерируется из OpenAPI, перегенерируете типы и SDK.
  3. TypeScript показывает места, где старый код больше не сходится с новым контрактом. Чаще всего это ACL-мапперы и вызовы в data-access слое.
  4. Прогоняете тесты и проверяете стенд, на котором крутится совместимая версия BFF или API. Нельзя выкатывать фронтенд, собранный под контракт 2.x, на стенд, где ещё живёт сервис 1.x.

Стенды и совместимость

Файлы environment и application config задают, куда именно ходит приложение: base URL, набор providers, иногда feature flags. Это как раз место для DIP. А вот совместимость версий — отдельная дисциплина релиза: тег клиента в репозитории фронтенда и фактическая версия сервиса на стенде должны договариваться заранее.

Если пришёл MAJOR, вариантов несколько: versioned endpoint вроде /v2, параллельный пакет клиента, временная поддержка двух форм в маппере, либо согласованное окно, когда фронт и бэкенд выкатываются вместе. На интервью полезно проговорить не только «подниму тег», но и «как пойму, что стенд ещё не готов к этой версии».

Здесь снова встречаются Protected Variations и ACL. UI зависит от относительно стабильных моделей экрана. Ломается и чинится граница data-access, когда вы обновляете тег зависимости. Именно поэтому маппер и сгенерированный клиент так важны: они принимают удар контрактных изменений первыми.

Короткий ответ на собеседовании примерно на полторы минуты

Ниже не список терминов, а связный каркас. Его можно проговорить своими словами.

  1. Если в workspace несколько Angular-приложений, я отношусь к ним как к разным Bounded Contexts: общий ui-kit и инфраструктура допустимы, а вот одна доменная модель на все продукты обычно вредна.
  2. При большом числе API я не зову микросервисы прямо из компонентов. Между UI и сетью живут data-access и ACL-маппер. Если экран требует тяжёлой агрегации или разные приложения хотят разный shape данных, я рассматриваю BFF по определению Newman и Microsoft.
  3. Различия стендов выношу в environment и DI-providers. Компоненты зависят от абстракций вроде base URL и портов, а не от строки с именем стенда.
  4. Когда бэкенд подключен как зависимость по тегу, я опираюсь на SemVer: смотрю diff контракта, обновляю клиент и мапперы, проверяю совместимость версии сервиса на целевом стенде.
  5. Внутри фичи думаю языком GRASP: компонент и facade как Controller, правила рядом с данными как Information Expert, API и interceptor как Pure Fabrication, а граница с нестабильными сервисами — как Protected Variations.

Как создавать своё: не выучить названия, а повторить ход мысли

Принципы и паттерны не появляются из воздуха. Сначала есть повторяющаяся боль, потом появляется именованный приём, который эту боль локализует. На интервью сильный ответ звучит так: «вот какая проблема была → вот какую границу мы провели → вот как это выглядит в Angular». Ниже — рабочий способ придумать решение под свой проект, даже если готового слова из учебника ещё нет.

Общий рецепт на один экран или одну фичу

  1. Соберите симптомы. Что ломается чаще всего: контракт API, вёрстка, правило отмены, конфиг стенда, склейка нескольких запросов? Запишите это простыми предложениями, без модных терминов.
  2. Найдите ось изменения. Спросите: «если завтра поменяется только X, какие файлы придётся трогать?» Если ответ «половину приложения», граница проведена плохо.
  3. Проведите шов. Вынесите нестабильное за интерфейс, token, mapper, отдельный сервис или BFF. Стабильным оставьте сценарий экрана и язык продукта.
  4. Назовите роль, а не технологию. Сначала скажите «это контроллер сценария» или «это антикоррупционный слой», и только потом выбирайте SignalStore, interceptor или Nest-BFF.
  5. Проверьте на маленьком примере. Подмените стенд, обновите тег API, добавьте второй способ оплаты. Если изменение локально — шов работает. Если снова правите всё подряд — шов декоративный.

Как «изобрести» свои правила команды

Вам не нужно придумывать новый SOLID. Нужно зафиксировать правила, которые повторяют ту же логику на языке вашего репозитория. Например:

  • «Компонент не импортирует HttpClient напрямую» — это локальная форма Controller + Indirection.
  • «Каждый внешний DTO проходит через mapper» — это локальная форма ACL и Protected Variations.
  • «Новый стенд = новый набор providers, без if по имени» — это локальная форма DIP.
  • «MAJOR тега API требует отдельного PR с обновлением мапперов и smoke на совместимом стенде» — это локальная форма SemVer-дисциплины.

Хорошее командное правило короткое, проверяемое в code review и привязано к конкретной боли. Плохое правило звучит как «пишите чисто» и никого ничему не обязывает.

Мини-лаборатория: соберите архитектуру с нуля

Возьмите вымышленный экран «Карточка заказа» для двух приложений: client-portal и ops-admin. Данные приходят из трёх сервисов, на stage и prod разные base URL, а клиент API обновляется тегами.

  1. Разведите две модели заказа, если язык продуктов разный. Не тащите один shared Order на оба app.
  2. В каждом app сделайте цепочку: component → facade → api client → toOrder mapper.
  3. Если склейка трёх сервисов болезненная, опишите BFF-контракт под экран и пусть Angular зависит только от него.
  4. Вынесите API_BASE_URL и, при необходимости, auth-адаптер в providers стенда.
  5. Проиграйте обновление API с 1.4.2 на 2.0.0: где должен покраснеть TypeScript, какой стенд ещё нельзя трогать, что правите в первую очередь.

Если после этого упражнения вы можете объяснить решение словами «здесь Expert, здесь ACL, здесь BFF, здесь SemVer», значит тема уже не чужая: вы не заучили ярлыки, а повторили ход мысли авторов этих идей.

Частая ошибка: принципы как украшение

Можно развесить слова SOLID и DDD по README и при этом оставить бог-компонент с десятком HTTP-вызовов. Принцип полезен только если он меняет конкретное решение: куда положить функцию, какую зависимость инжектить, какой пакет версионировать, где проходит граница приложения. На собеседовании лучше один живой пример из Angular, чем пять правильных определений без применения.
