SOLID · оформление классов

S — Single Responsibility

Одна ось изменений. OrderListComponent — UI, OrderApiService — HTTP, facade — сценарий экрана. Не тащи API + localStorage + скидку в компонент.

O — Open/Closed

Новый способ оплаты = новая стратегия + provide, а не if (type === 'sbp') в старом сервисе. Interceptors — расширение пайплайна без правки HttpClient.

L — Liskov

Подмена реализации не ломает контракт. Любой interceptor должен вернуть поток событий; DevTokenProvider и ProdTokenProvider — один смысл токена.

I — Interface Segregation

Не гигантский IBackendApi. Отдельные OrdersApi, UsersApi, CatalogApi.

D — Dependency Inversion

Facade зависит от PAYMENT_PORT, а не от Stripe-класса. Стенды = разные providers на один токен, без if (environment.name) в компонентах.

GRASP · кто за что отвечает

SOLID — форма. GRASP — распределение ответственности. Девять шаблонов, сгруппированных как в разборе на Хабре.

High Cohesion / Low Coupling

Feature orders/ про заказы. Не импортирует внутренности billing/ — только публичный API. В monorepo UI-kit можно шарить, домен — осторожно.

Information Expert

Поведение рядом с данными: order.canCancel() или pure-функция у типа, а не копипаста правила в трёх компонентах. Анемичная модель + бог-сервис — антипаттерн.

Creator

Создаёт ближайший владелец: store/mapper делает OrderVm из DTO, компонент не вызывает new Order().

Controller

UI-controller — компонент (клик → facade). Use-case controller — facade/effect сценария. Плохо: компонент на 400 строк с бизнес-логикой.

Pure Fabrication

Искусственные объекты ради архитектуры: ApiService, Interceptor, ErrorMapper, SignalStore. В бизнесе их нет — в коде они держат cohesion/coupling.

Indirection

Прослойки: facade, BFF, DTO→VM mapper, interceptor. Adapter/Facade/Proxy — частные случаи.

Polymorphism + Protected Variations

Разное поведение через контракт. Защита ядра UI от нестабильных 20 API и тегов бэка — data-access + маппинг + абстракция URL + часто BFF.

Связка: OCP ≈ Polymorphism + Protected Variations; DIP ≈ Indirection + PV; SRP ≈ High Cohesion + Expert.

DDD · Strategic Design

Ubiquitous Language

Одинаковые слова с бизнесом. В клиенте «Заказ», в админке «Заявка» — разные модели, даже если JSON похож.

Bounded Context

client-portal, partner-cabinet, ops-admin — разные контексты. Один Customer ≠ одна shared-модель на все apps.

Context Map

Customer/Supplier, Conformist (фронт подстраивается под API), Anti-Corruption Layer, Shared Kernel (редко). ACL на фронте = toOrder(dto).

Monorepo-правило

Shared: ui-kit, auth, logging. Не shared: «божественная» доменная модель на все проекты.

BFF · Backend for Frontend

Легковесный сервис под конкретный клиент: ходит в микросервисы, собирает и форматирует данные под экран, отдаёт один удобный контракт. Не второй монолит и не место для тяжёлого домена.

Без BFF

  • Angular сам клеит 8–15 API
  • waterfall и хрупкие экраны
  • ломка при каждом микросервисе

С BFF

  • Один OrdersBffClient на экран
  • Типы от OpenAPI BFF
  • Стенд смотрит на URL BFF стенда

Gateway маршрутизирует и режет трафик. BFF собирает контракт под UI. Angular service — только клиент.

Версионирование · бэкенд как зависимость

В репо фронта лежит клиент/OpenAPI как пакет или git-зависимость, обновление по тегу (@company/orders-api@1.8.3).

MAJOR ломающий контракт
MINOR совместимое добавление
PATCH фикс без смены контракта
  1. Подняли tag в package.json / lockfile
  2. Перегенерили клиент / типы
  3. Починили красный TypeScript
  4. Проверили стенд с совместимой версией бэка

Не деплоить фронт, требующий новых полей, на стенд со старым API. Breaking → versioned route или параллельный пакет.

Ответ на 90 секунд

  1. Несколько Angular apps ≈ Bounded Contexts; shared только инфраструктура и UI-kit.
  2. Много API → data-access + ACL; тяжёлая склейка экрана → BFF.
  3. Стенды → DI + environments, не if по имени стенда в UI.
  4. Бэкенд по тегам → SemVer, diff контракта, согласованный деплой.
  5. Внутри фичи: Controller / Expert / Pure Fabrication / Low Coupling.
