SOLID

SOLID — пять принципов объектно-ориентированного проектирования, сформулированных Робертом Мартином (Uncle Bob). Фокус — управление зависимостями: код должен оставаться изменяемым без хрупкости и каскадных правок.

Solid Relevance (Martin) SRP OCP Wikipedia: SOLID Angular DI

S — Single Responsibility Principle

«Gather together the things that change for the same reasons. Separate things that change for different reasons.» — Robert C. Martin, Solid Relevance

Классическая краткая формулировка: у модуля должна быть одна причина для изменения. Это не «один метод в классе», а одна ось изменений (UI, HTTP-контракт, правила отмены заказа — разные оси).

В Angular

  • OrderListComponent — отображение и пользовательские события списка.
  • OrdersApi (providedIn: 'root' или feature providers) — только HTTP к orders.
  • Facade / SignalStore — сценарий экрана: загрузка, ошибки, навигация после действия.
  • Mapper toOrder(dto) — отдельный модуль: меняется при смене DTO, не при смене CSS.

Нарушение: компонент сам вызывает HttpClient, мапит ответ, считает скидку и пишет в localStorage. Любое изменение API, UI или правил хранения трогает один файл.

O — Open/Closed Principle

«A Module should be open for extension but closed for modification.» — Robert C. Martin, Solid Relevance

Новое поведение добавляют расширением (новая реализация / конфигурация), а не правкой уже работающего кода клиента абстракции.

В Angular

  • Стратегии оплаты: интерфейс / token PAYMENT_STRATEGY, новые классы + provide, без разрастания switch в старом сервисе.
  • HTTP-пайплайн расширяется через provideHttpClient(withInterceptors([...])) — новый interceptor не переписывает HttpClient.
  • Новый стенд = новый environment / набор providers, а не ветвления внутри feature-сервисов.

L — Liskov Substitution Principle

«A program that uses an interface must not be confused by an implementation of that interface.» — Robert C. Martin, Solid Relevance

Исторически связан с подстановкой Барбары Лисков: объекты подтипа должны быть заменяемы на объекты супертипа без нарушения корректности программы. В DI-терминах: любая реализация токена должна соблюдать контракт, на который рассчитывает потребитель.

В Angular

  • Functional interceptor обязан принять запрос и вернуть Observable<HttpEvent> через next — «особый» interceptor, который глотает ошибки без договорённости, ломает ожидания пайплайна. См. HTTP interceptors.
  • AuthTokenProvider для dev и prod: оба должны отдавать токен того же смыслового контракта (или явно документировать отличие), иначе facade «ломается» только на одном стенде.

I — Interface Segregation Principle

«Keep interfaces small so that users don’t end up depending on things they don’t need.» — Robert C. Martin, Solid Relevance

В Angular

  • Не один BackendApi на 80 методов. Отдельные OrdersApi, CatalogApi, UsersApi.
  • Feature «каталог» зависит только от catalog-клиента — при MAJOR в orders-пакете каталог не обязан обновляться.
  • В monorepo: публичный API библиотеки через index.ts / secondary entry points, без экспорта внутренних mapper’ов наружу.

D — Dependency Inversion Principle

«Depend in the direction of abstraction. High level modules should not depend upon low level details.» — Robert C. Martin, Solid Relevance

Высокоуровневая политика (сценарий checkout) не должна импортировать низкоуровневую деталь (конкретный HTTP-клиент Stripe). Оба зависят от абстракции (порт / token).

В Angular — это буквально DI-фреймворк

  • Документация: Dependency injection in Angular, Defining dependency providers, InjectionToken.
  • Высокий уровень: CheckoutFacade делает inject(PAYMENT_PORT). Низкий уровень: { provide: PAYMENT_PORT, useClass: StripeAdapter } в app.config.ts / environment providers.
  • Разные стенды: один facade, разные значения API_BASE_URL и адаптеров — без if (environment.name === 'stage2') внутри компонентов. 
export const API_BASE_URL = new InjectionToken<string>('API_BASE_URL');

export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(withInterceptors([authInterceptor])),
    { provide: API_BASE_URL, useValue: environment.apiBaseUrl },
  ],
};

GRASP

GRASP (General Responsibility Assignment Software Patterns / Principles) — девять фундаментальных принципов назначения ответственности объектам. Введены Крэгом Ларманом в книге Applying UML and Patterns. SOLID отвечает на «как оформить зависимости», GRASP — на «кому дать работу».

Wikipedia: GRASP Larman, ch.16 (O’Reilly)

High Cohesion / Low Coupling

High Cohesion — обязанности элемента сфокусированы и связаны между собой. Low Coupling — элемент имеет мало зависимостей от других элементов; изменения локализуются. — GRASP / Larman (см. обзор)

В Angular

  • Feature-папка / library orders: routes, components, facade, api — про заказы.
  • Не импортировать deep-пути соседней фичи (billing/internal/...) — только публичный API lib.
  • В workspace с несколькими projects: общая UI-kit библиотека — нормально; общая «божественная» доменная модель на все apps — повышает coupling.

Information Expert

«Assign a responsibility to the information expert — the class that has the information necessary to fulfill the responsibility.» — Craig Larman, Information Expert (Applying UML and Patterns)

В Angular

  • Правило «можно ли отменить заказ» живёт рядом с данными заказа: метод/pure-функция у модели/VM, а не копипаста в трёх компонентах.
  • Анемичный DTO + «бог-сервис» на все правила — типичное нарушение Expert.
  • Исключение: если Expert тянет инфраструктуру (сохранение в БД) — см. Pure Fabrication / SRP.

Creator

Ответственность за создание экземпляра B назначают классу A, если A содержит / агрегирует B, активно использует B, или имеет данные инициализации B (упрощённо — частный случай Expert для создания). — GRASP Creator (Larman)

В Angular

  • Store/facade или mapper создаёт OrderVm из DTO — он владеет коллекцией и данными инициализации.
  • Компонент не делает new Order(...) из сырого JSON ответа.
  • Angular DI — отдельный механизм жизненного цикла сервисов; Creator про доменное создание объектов в сценарии, не про providedIn.

Controller

Назначить ответственность за обработку системного события объекту, представляющему систему / сценарий use-case (первый объект за UI или другим входом, который координирует работу). — GRASP Controller (Larman)

В Angular

  • UI-уровень: компонент принимает клик/сабмит и делегирует дальше — сам не содержит бизнес-сценарий.
  • Application-уровень: facade / effect / use-case service: «оформить заказ» = валидация состояния → вызов API → обновление signals → router.navigate.
  • Плохой Controller: компонент на сотни строк с ветвлением бизнес-правил и несколькими HTTP-вызовами.

Pure Fabrication

Создать искусственный класс, которого нет в предметной области, чтобы поддержать high cohesion / low coupling и не загрязнять domain-объекты инфраструктурой. — GRASP Pure Fabrication (Larman)

В Angular

  • OrdersApi, functional interceptor, ErrorMapper, SignalStore / NgRx — fabrication’ы.
  • Они не «заказ» и не «клиент» в языке бизнеса, но держат инфраструктурные обязанности отдельно от UI и правил домена.

Indirection

Назначить ответственность промежуточному объекту, чтобы развязать (decouple) другие компоненты. — GRASP Indirection (Larman)

Adapter, Facade, Proxy, Repository — часто реализации идеи Indirection.

В Angular

  • Facade между компонентом и несколькими API-сервисами.
  • Mapper DTO → VM между сырым контрактом пакета API и шаблоном.
  • Interceptor между feature-кодом и транспортом HTTP.
  • BFF между Angular-приложением и набором микросервисов.

Polymorphism

Когда поведение зависит от типа, назначать ответственность полиморфным операциям — альтернативы через подстановку реализаций, а не через разрастающиеся условные ветки по типу. — GRASP Polymorphism (Larman)

В Angular

  • Разные реализации PriceStrategy / feature providers для retail vs partner apps в одном monorepo.
  • Разные auth-адаптеры по стенду через один token.

Protected Variations

Идентифицировать точки вероятных изменений и обернуть их стабильной интерфейсной точкой, чтобы вариации не «пробивали» клиентов. — GRASP Protected Variations (Larman); тесно связан с OCP / DIP

В Angular (критично для multi-API / multi-stand)

  • Нестабильно: контракты 10–20 сервисов, URL стендов, форматы ошибок, теги бэкенд-пакетов.
  • Стабильно для UI: сценарии экранов и типы VM фичи.
  • Защита: слой data-access, mapper, InjectionToken для base URL, клиент/OpenAPI по зафиксированному тегу, при необходимости — BFF с контрактом под Angular-app.
Связка с SOLID: OCP достигается через Polymorphism + Protected Variations; DIP — через Indirection + PV; SRP — через High Cohesion + Information Expert.

DDD · Strategic Design

Domain-Driven Design — подход Эрика Эванса: сложность ПО снижается фокусом на предметной области и явной модели, выраженной в коде и в языке команды. Strategic Design — часть DDD про крупные границы: где модель едина, а где нужны отдельные модели и карты связей.

domainlanguage.com (Evans) Fowler: Bounded Context DDD Community

Ubiquitous Language

Единый язык модели, на котором говорят разработчики и эксперты предметной области; термины языка напрямую отражаются в коде модели. — Eric Evans, Domain-Driven Design

В Angular

  • Имена типов, сигналов, route data и сообщений об ошибках совпадают с языком продукта («Заказ», «Черновик», «Отгрузка»).
  • Если в admin говорят «Заявка», а в client — «Заказ», это сигнал разных контекстов: не форсировать один shared-тип.

Bounded Context

«A description of a boundary (typically a subsystem, or the work of a particular team) within which a particular model is defined and applicable.» — Eric Evans; также: «explicit boundary within which a domain model exists… Ubiquitous Language have specific meaning» — Vaughn Vernon, IDDD

Martin Fowler: Bounded Context — центральный паттерн strategic design; большая система делится на контексты с явными взаимосвязями, потому что полная унификация модели обычно нереалистична. Источник: martinfowler.com/bliki/BoundedContext.

В Angular workspace

  • apps/client-portal, apps/partner-cabinet, apps/ops-admin — кандидаты в разные Bounded Contexts.
  • Один JSON-поле customer с бэка не означает одну модель TypeScript на все apps.
  • Структура: libs/client-portal/orders и libs/partner-cabinet/deals — свои модели; libs/shared/ui-kit — общее UI; libs/shared/auth — инфраструктура (осторожно с доменом).

Context Map и отношения

Context Map фиксирует Bounded Contexts и отношения между ними (кто upstream/downstream, как интегрируются модели). — Evans, Part IV Strategic Design; Vernon, IDDD ch.3
  • Customer/Supplier — upstream задаёт контракт, downstream потребляет (часто команда API → Angular-команда).
  • Conformist — downstream принимает модель upstream «как есть» (типично при жёстком OpenAPI без влияния фронта).
  • Anti-Corruption Layer (ACL) — слой перевода, чтобы чужая модель не протекала внутрь контекста.
  • Shared Kernel — маленькое genuinely общее ядро; не путать с папкой shared/ на всё подряд.

ACL во фронтенде

// контракт зависимости / OpenAPI
type OrderDto = { order_id: string; status_code: number };

// модель контекста Angular-приложения
type Order = { id: string; status: 'new' | 'paid' | 'cancelled' | 'unknown' };

export function toOrder(dto: OrderDto): Order { /* ... */ }

Mapper + типы VM — практический ACL: шаблоны и facade зависят от Order, а не от status_code пакета API. При обновлении тега зависимости чините ACL, а не полприложения.

BFF · Backend for Frontend

Паттерн архитектурный: отдельный backend-сервис (или слой) под конкретный frontend/interface, вместо одного general-purpose API на все клиенты.

Microsoft Learn: Backends for Frontends Sam Newman: BFF Habr: BFF (обзор)

Определение (Microsoft Azure Architecture Center)

«Create a separate backend service for each frontend interface, instead of using a single general-purpose backend for all of them. This approach lets you tailor each backend to the needs of its frontend…» — Backends for Frontends pattern; основано на паттерне Sam Newman

Проблема: несколько клиентов (web/desktop/mobile) давят на один backend разными требованиями к payload, пагинации, производительности → узкое место и конфликт релизов. Решение: слой BFF между клиентом и доменными сервисами; при нескольких интерфейсах — часто по BFF на интерфейс.

Что Microsoft явно рекомендует помнить

  • BFF должен содержать client-specific логику UX; cross-cutting (auth perimeter, rate limit, routing) — отдельно (gateway / gatekeeper).
  • Дублирование кода между BFF’ами — ожидаемый trade-off.
  • Лишняя сеть hop → latency; не плодить BFF без нужды.
  • Если клиенты ходят почти одинаково — один shared backend / gateway может быть достаточным.

Как это стыкуется с Angular

  • Angular-app зависит от одного стабильного контракта BFF (OpenAPI → сгенерированный клиент), а не от 10 клиентов микросервисов в каждом экране.
  • В коде: OrdersBffClient / provideHttpClient + base URL стенда BFF (HttpClient guide).
  • Facade остаётся use-case controller’ом: вызывает BFF-методы под экран, обновляет signals. Агрегация «склеить профиль + заказ + платежи» по возможности на BFF, не waterfall’ом из компонента.
  • Несколько Angular projects: client-portal BFF и admin BFF могут быть разными сервисами/пакетами (разные интерфейсы → разные BFF по определению паттерна).

Angular data-access без BFF

  • Несколько *Api сервисов
  • Склейка в facade
  • UI чувствителен к ломке каждого микросервиса

Angular + BFF

  • Один клиент контракта экрана/канала
  • Агрегация/формат на сервере
  • Protected Variations для UI

Версионирование · бэкенд как зависимость по тегам

Когда OpenAPI-клиент / npm-пакет / git-dependency бэкенда лежит в репозитории Angular-приложения и обновляется по git/npm tag, вы версионируете публичный контракт на границе контекста.

Semantic Versioning 2.0.0 npm: About semantic versioning npm package.json dependencies

Определение SemVer

Given a version number MAJOR.MINOR.PATCH, increment the:
1. MAJOR version when you make incompatible API changes
2. MINOR version when you add functionality in a backward compatible manner
3. PATCH version when you make backward compatible bug fixes — semver.org (Tom Preston-Werner)
  • ПО, использующее SemVer, MUST объявить публичный API (документация и/или код).
  • После релиза содержимое версии MUST NOT меняться — любые правки = новая версия.
  • 0.y.z — начальная разработка, API может быть нестабильным.

Как это выглядит в Angular-репозитории

// package.json
{
  "dependencies": {
    "@company/orders-bff-client": "1.8.3",
    "@company/catalog-api": "git+ssh://git@github.com/company/catalog-api.git#v3.2.1"
  }
}
  1. Обновить tag / версию в package.json и lockfile.
  2. Перегенерировать клиент/типы из OpenAPI (если генерация в CI/local script).
  3. TypeScript подсветит несовместимости в ACL/facade — починить mapper и вызовы.
  4. Прогнать тесты; выкатить на стенд, где крутится совместимая версия BFF/API.

Стенды

  • environment.ts / configuration задаёт apiBaseUrl и связанные providers (DIP).
  • Версия npm-клиента и версия сервиса на стенде должны согласовываться: фронт, собранный под 2.x контракт, нельзя деплоить на стенд с API 1.x.
  • Breaking (MAJOR): versioned endpoint (/v2), параллельный пакет, или период dual-support в ACL.

Связь с Protected Variations и ACL: UI зависит от стабильных VM-типов; ломается и чинится граница data-access при обновлении тега зависимости.

Каркас ответа на собеседовании (~90 сек)

  1. Несколько Angular apps — разные Bounded Contexts; shared — ui-kit и инфраструктура, не вся доменная модель.
  2. Много API → data-access + ACL mapper; тяжёлая агрегация под экран → BFF (Newman/Microsoft).
  3. Стенды → InjectionToken + environment providers (DIP), не ветвление по имени стенда в UI.
  4. Бэкенд-пакет по тегам → SemVer, diff контракта, согласованный деплой фронт↔API.
  5. Внутри фичи: Controller (facade), Information Expert (модель), Pure Fabrication (api/interceptor), Low Coupling между libs.
